# Аудит інтерфейсу і бази даних

Систему пройдено від імені кожної ролі за повним циклом кампанії: підготовка → подання → розгляд → голосування →
підрахунок → визначення переможців → реалізація → закриття. Демо-дані: `reset.bat`, логіни в README.

Правила звірено з ТЗ (ч.1 п.4.2 — 24 задачі, ч.2 п.2.1 — бізнес-правила, ч.2 п.3.3 — безпека) і прецедентами
ПЦ-01…ПЦ-20, ДП-01…ДП-23. Де «Тема, мета» розходиться з ТЗ, взято формулювання ТЗ (див. розділ 3).

Пріоритети: **P1** — порушує правило ТЗ або може зіпсувати дані чи демонстрацію; **P2** — незручно або неконсистентно,
користувач може помилитися; **P3** — косметика.

Стан: ✔ — виправлено в цій версії, ○ — свідомо лишено (з причиною).

## 2. База даних

### Склад (`CivicBudget_create.sql`, без змін)

| Об'єкт | Кількість | Примітка |
|---|---|---|
| Таблиці | 20 | довідники, користувачі й ролі, кампанії, проєкти, голосування, реалізація, сповіщення й аудит |
| Первинні ключі | 20 | сурогатні `IDENTITY`, у `UserRole`, `CampaignCategory`, `Subscription` — складені |
| Зовнішні ключі | 36 | 11 з дією при видаленні (нижче), решта `NO ACTION` |
| UNIQUE | 9 + 3 фільтровані унікальні індекси | `Email`, `IdentityHash`, `RegNumber` можуть бути NULL |
| CHECK | 38 | переліки статусів, діапазони, порядок дат, залежні поля |
| DEFAULT | 30 | статуси, дати, ліміти голосування |
| Індекси | 22 | під фільтри каталогу, черги, аудит; INCLUDE, фільтровані, просторовий `SIX_Project_Location` |
| Представлення | 3 | `vw_ProjectCost`, `vw_ProjectResult`, `vw_ImplementationProgress` |
| Тригери | 2 | `TR_Vote_CheckRules` (50001–50005), `TR_Project_StatusChange` (аудит + сповіщення) |
| Процедури | 2 | `usp_SubmitProject` (50010–50015), `usp_SelectWinners` (50020) |

### Дії при видаленні

| Зовнішній ключ | ON DELETE | Чому |
|---|---|---|
| `UserRole`, `Subscription`, `Notification` → `UserAccount` | CASCADE | ролі, підписки й особисті сповіщення без користувача не мають сенсу |
| `CampaignCategory` → `Campaign` | CASCADE | ліміти — частина кампанії |
| `BudgetItem`, `Attachment`, `Subscription` → `Project` | CASCADE | кошторис і вкладення — частина проєкту (видалити можна лише чернетку) |
| `Notification` → `Project` | SET NULL | сповіщення лишається в історії користувача |
| `ImplementationStage` → `Implementation`, `Report` → `ImplementationStage`, `Attachment` → `Report` | CASCADE | етапи, звіти й фото належать картці реалізації |
| усі інші, зокрема `Vote`, `Review`, `AuditLog`, `Implementation` | NO ACTION | історичні дані не видаляються: не можна видалити користувача з голосами, проєкт з рецензіями чи голосами, кампанію з проєктами |

`AuditLog.UserId` навмисно без каскаду: журнал має пережити будь-які зміни. Голоси не видаляються, тому
відкликати голос в інтерфейсі не можна (V1).

### Чого бракувало з переліку об'єктів лекції 6

| Об'єкт | Було | Зроблено |
|---|---|---|
| Таблиці, ключі, обмеження, індекси, представлення | є | — |
| Збережені процедури, тригери, транзакції, обробка помилок `THROW` | є | — |
| **Функції користувача** (скалярна і таблична) | немає | `dbo.fn_RemainingVotes`, `dbo.fn_CategoryBudgetBalance` в `db/CivicBudget_v2_extensions.sql` |
| Ролі БД і права (`GRANT`) | немає | ○ застосунок працює під одним обліковим записом Windows; рекомендація для промислового розгортання — у `docs/dba-guide.md` |
| Резервне копіювання | немає | ○ команди `BACKUP` / `RESTORE` — у `docs/dba-guide.md` |

Нові об'єкти не змінюють жодної з 20 таблиць і лежать в окремому скрипті, який `reset.ps1` запускає між create і demo.
